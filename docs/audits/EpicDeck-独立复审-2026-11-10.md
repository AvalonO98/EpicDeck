**一个必须记住的坑**（我第一轮就踩了）：合成按钮事件必须用 `vgp_onbuttondown`。用 `vgp_ongamepadbutton` 派发时事件确实冒泡到了 `.ed-surface`（我加了监听确认），但**没有任何处理器响应**，看起来就像"L1 坏了"——差一点写出一个假 bug。以后写探针先 `getEventListeners(el)` 看一眼真实事件名。

**复现两条关键探针**（可直接贴进 `cdp_eval.py`）：

```js
// 1.2 容器锚点：focusin 序列必须是 [ed-surface, 原控件]
const s = document.querySelector('.ed-surface'); const seen = [];
const spy = e => seen.push((e.target.className || '').slice(0, 20));
window.addEventListener('focusin', spy, true);
s.setAttribute('tabindex', '0'); s.focus(); s.removeAttribute('tabindex');
window.removeEventListener('focusin', spy, true);
console.log(seen);  // ["ed-surface ...", "ed-tile ..."]

// 1.5 切标签光标跟随
window.__epicdeckTab(1);
await new Promise(r => setTimeout(r, 300));
console.log(document.activeElement.getAttribute('data-ed-tab')); // "downloads"
```

## 4. 本轮新发现

### 4.1 ✅ 已实机排除：按钮事件不会被原生控件吞掉

原本的担心：beta.6 只把**方向键**搬到了 window 捕获阶段，A / B / L1 / R1 仍然挂在 `.ed-surface` 的 `onButtonDown` / `onCancel` 上（`fullscreen.tsx:3035-3057, 3089-3100`），如果 Steam 原生控件连按钮事件也消费，就会出现"焦点在开关上时 B 退不出、L1/R1 不切页"。

**实机验证（2026-11-10 23:47，beta.6）**——先用 `getEventListeners(.ed-surface)` 确认了 Decky 注册的真实事件名（这很关键，我第一轮用了 `vgp_ongamepadbutton`，**根本没人监听**，差点误判成"L1 坏了"）：

```
vgp_requestfocus / vgp_ondirection / vgp_onbuttondown / vgp_oncancel
（焦点元素上另有 vgp_onok，即 A 的"激活"事件）
```

然后分别派发：

| 动作 | 目标 | 结果 |
|---|---|---|
| L1（`vgp_onbuttondown` button 6） | 原生 ToggleField（`role=checkbox`） | 设置 → 游戏库，标签切换成功，焦点跟到"游戏库" chip ✅ |
| B（`vgp_oncancel`） | 详情页原生 `<input>` | 详情关闭，焦点回到原封面 ✅ |
| A（`vgp_onok`） | 原生 ToggleField | `aria-checked` false → true → false（一次一翻）✅ |
| A（`vgp_onbuttondown` button 1） | 封面 tile | 详情打开，焦点落在「下载并安装」✅ |

结论：**按钮类事件照常冒泡到 surface，§4.1 的风险不存在**，不需要把 A/B/L1/R1 也搬进捕获阶段。唯一没测到的是"下拉菜单展开后用摇杆上下选项"（菜单在 popup 层，理论上在 `.ed-surface` 外），留给下一次顺手确认。

### 4.2 【P2】"取消并删除"仍有一个极早取消的空档

`main.py:2597-2628`：只有找到一个**真实存在的候选目录**并删掉后，才允许删 `.resume`；但判断写的是 `if not removed_any and candidates: return`。当 `candidates == []` 时（下载刚开始、legendary 还没打印 `Install path:`，`installed.json` 没记录，`install_targets` 也因为老配置缺失）→ 直接往下走，删 `.resume` 而不删目录——正是上一轮 3.3 描述的"空间没释放、续传也没了"。

改法：`if not removed_any: return`（不管 `candidates` 是否为空）。

### 4.3 【P3】L1/R1 在工具栏翻页会把光标拽进网格

`flipPageAndFocus` 用 `activeElement` 算列；焦点在工具栏 chip / 排序 / 翻页键上时 `grid` 为 null → `col = 0` → 翻页后把光标放到第 1 张封面（`fullscreen.tsx:2592-2610`）。旧行为是"翻页但光标留在工具栏"。

不算 bug，但会让"连按 R1 浏览页码"变成"光标突然掉进内容区"。建议：`from` 不在网格里时，翻页后不落焦（或把焦点放回原元素，如果它还在）。

### 4.4 【P3】网格"上"可能落在一个已经失效的控件上

`gridEntryRef` 只校验 `isConnected` + 在 surface 内 + 不在网格内（`fullscreen.tsx:2866-2872`），没有重新校验"它现在还能不能被聚焦/激活"。典型场景：焦点在"下一页"箭头上 → 下进网格 → L1 翻回第 1 页（此时"上一页"变 `aria-disabled` + `tabIndex=-1`）→ 按"上"→ 光标落到这个禁用箭头上，按 A 没反应（但导航本身还能继续，因为它是 leaves）。

改法：`usable(entry, root) && entry.matches(CANDIDATE_SELECTOR)`。

### 4.5 【P2 / 归因需修正】插件卸载 5 秒被杀：不是 EpicDeck 慢，是 Decky 停服时序

我用 journalctl 把三次卸载都翻出来了：

```
23:15:47  Stopping response listener for EpicDeck (v0.9.5-beta.5)
23:15:47  EpicDeck unloaded
23:15:47  Plugin EpicDeck (v0.9.5-beta.5) has been stopped in 0.1s      ← 单独停插件：0.1s，干净

23:21:26  Plugin EpicDeck (v0.9.5-beta.5) still alive 5 seconds ... SIGKILL   ← 这两次都是
23:28:32  Plugin EpicDeck (v0.9.5-beta.5) still alive 5 seconds ... SIGKILL      systemctl restart plugin_loader
23:28:32  Plugin Freedeck (v0.6) still alive 5 seconds ... SIGKILL      ← 同一秒，另一个插件也一样
```

结论修正：**单独 stop 只要 0.1s**（`_unload` 本身没问题）；只有**整个 `plugin_loader` 重启**时才 5.1s 被 SIGKILL，而且 **Freedeck 在同一秒出现同一条警告**。所以这更像 Decky 停服时"先掐 RPC/事件循环、再等插件 unload"的时序问题，而不是 EpicDeck 的 `_unload` 阻塞。HANDOFF 7.30 里"怀疑是同步 HTTP/线程池未 join"的方向可以暂缓。

仍然建议（低成本、防未来）：给 `_unload` 的 `await _stop_login_session()` 套 `asyncio.wait_for(…, 3)`，把 `statvfs`/VDF 写盘搬进 executor，并在 `_main`/`_unload` 各打一行耗时日志——这样下次再出现 5s，日志能直接区分"是我们慢"还是"回调根本没被调度"。

### 4.6 【P3】调试入口的重挂方式

`fullscreen.tsx:2706-2745` 的 effect **没有依赖数组** → 每次渲染都卸载/重挂 `__epicdeckNavRC`、`__epicdeckBump`、`__epicdeckTab`、`__epicdeckDiag`。功能上没问题（注释说明了原因），但如果 CDP 恰好在"卸载后、重挂前"调用会拿到 undefined。建议改用 `useEffect(() => {...}, [tab, viewport])` 或 ref 转发。

### 4.7 【P3】小残留

- `.ed-row` 的 CSS 规则还在（`components.tsx:26, 118-120, 164, 171`），但已经没有任何元素用这个类；
- `data-ed-own` 只出现在 A 白名单里，没有元素使用（预埋钩子）；
- `index.tsx:4-5` 顶部注释仍说"add the Steam-menu shortcut"；`onDismount` 里留着注释掉的 `uninstallMenuEntry()`；
- `_pump_install_log` 与 `_install_streaming` 都会 pop `_live_progress`（双保险，无害）；
- `describeRows()` 在每次"没移动"的按键上跑一次全量候选聚类（:2909）。设置页 100+ 候选时是毫秒级，可接受，但这是排查代码，长期应放到开关后面；
- 实机日志里有一条 `protondb verdi: Steam 检索失败或超时 (title='Dragon Age: Inquisition – Game of the Year Edition')` —— ProtonDB 按标题检索对 GOTY 这类带后缀的名字仍会失手（不是本轮回归，属于已知的标题匹配脆弱）。

### 4.8 【P3】"吸收一次插队"的副作用：用户主动聚焦的第一下会被吞

实机观察到两次（都是脚本 `focus()`，但与触摸点击走同一路径）：**进设置页后第一次聚焦开关失败、焦点被拉回「切换账号」；按完"上"后第一次聚焦搜索框失败、焦点被拉回上一个控件**。第二次再聚焦就成功。

- 原因：`settleFocus` 的第 2 分支把"任何不是 `ownedTarget` 的 focusin"都当成 Steam 插队，拉回并消费一次（`geomnav.ts:168-181`）。这挡住了 Steam 的斜移，但**用户自己的下一次聚焦也会被当成插队**。
- 影响：触摸/鼠标用户点一个控件（开关、输入框、第二个封面）时，**点击本身生效**（click 事件不受影响），但焦点环留在上一个元素上；紧接着按 A 会作用在旧元素上。手柄用户不受影响（他们的移动都走 `focusOwned`）。
- 建议（小改）：在页面里捕获 `pointerdown` 记一个时间戳；`settleFocus` 第 2 分支若发现"最近 120ms 内有 pointerdown"，就**接受**这次 focusin 并把 `ownedSettled` 置真，而不是拉回。这样既能挡 Steam 的插队，又不跟用户的触摸抢焦点。

## 5. beta.6 新架构：window 捕获阶段接管 `vgp_ondirection` 的复核

这是本轮改动里**风险最高、价值也最大**的一处，单独看。

**实现**（`fullscreen.tsx:2967-2993`）：window 捕获阶段监听 `vgp_ondirection` → 仅当 `document.activeElement` 在 `.ed-surface` 内且是四个方向键时，转给 `dirHandlerRef.current`（每帧更新的最新 `onRootDirection`）。

**为什么它是对的**：

1. 捕获阶段（window）**先于**目标元素与冒泡阶段，所以 Steam 原生控件（target 内部）没有机会先处理；我们 `preventDefault + stopPropagation` 之后它们根本收不到；
2. 只接管"焦点在页面内"的按键，QAM / Steam 界面 / ConfirmModal（portal 在 surface 外）/ OSK（独立窗口）全部放行；
3. 保留了 `onGamepadDirection` 作兜底，两条入口共用同一个 `onRootDirection`，60ms 同键守卫去重——**不会双跳**；
4. 开关类控件的左右拨动通过"未移动 + `role=switch/checkbox/slider` 时不吞事件"恢复（:2939-2951）；7.33 实测"左把开关拨到另一个状态"成立。

**需要盯的边界**（按风险排序）：

| 边界 | 风险 | 怎么验 |
|---|---|---|
| ~~A/B/L1/R1 仍在组件层~~ | **已实机排除**（见 4.1）：原生 ToggleField 上的 L1 能切标签、原生 `<input>` 上的 B 能关详情、A 能翻开关 | 结论：不需要搬 |
| 下拉菜单展开后的上下导航 | 若菜单 DOM 在 `.ed-surface` 内，我们会接管它的方向键，菜单可能无法用摇杆选项 | 打开排序下拉，用摇杆上下选一项再按 A（**唯一没测到的边界**） |
| 长按连发 | 守卫 60ms 允许连发（和以前一致）；但"同键 60ms 内第二次"会被吞 | 快速连按左右两次看是否都生效 |
| 开关上的左右 | 放行后由 Steam 处理；若某个控件其实不处理左右，会"毫无反应" | 开关上左右各拨一次（7.33 已验"左把开关拨到另一个状态"） |
| 键盘用户 | `vgp_ondirection` 是手柄事件，键盘 ← → 不受影响 | 桌面模式用键盘试一次 |
